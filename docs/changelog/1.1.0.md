# 1.1.0 — full change record

The reviewed prose for every change in 1.1.0: the rationale, the trap each fix
closed, and the invariants each one established. This is the record. The
`1.0.0` record is [`1.0.0.md`](1.0.0.md), and the `0.16.0` line, which shipped
inside it, is [`0.16.0.md`](0.16.0.md).

[`CHANGELOG.md`](../../CHANGELOG.md) carries the *release note*, one line per
change, because that section is published verbatim as the GitHub release body,
and verification refuses a body over 125,000 characters. See
[`release-runbook.md`](../release-runbook.md) § Release-note hygiene.

Entries are in the order they were written, newest first.

- The `What this run established` block now says what it is not, ranks what it keeps, and the two answers that say the least say where they came from. Re-running the 23-PR public corpus after the block shipped found four ways a true block still misled a reviewer. (#812 follow-up; naming the changed files this entry does not read is #821)
  - **It is not the account of the change.** On one corpus pull request the block listed 17 items, named neither of the two files the change added — a hooks wiring file and a pin script — and showed three bare hook removals, inviting the reader to conclude the hooks were deleted rather than relocated. Every block now opens with one line saying what it lists: `only sources this entry read or tried to read are listed, so this is not the whole change: a changed file it does not read is absent`. It is not an item, is never dropped to make room for one, and appears in `diff`, `verify` text and the PR comment; `coverage.read_sources_only` says the same in JSON. Nothing new is discovered and no item is added.
  - **The cap keeps what a reviewer can act on.** On a refused comparison every item is a blocking limit, so the ten kept were decided by the source name: on one corpus repository 21 routine `unsupported` items sorted ahead of the single `unreadable` source and pushed it past the cap. Within the blocking limits the kind now decides — `unreadable`, `parse_failed`, `unresolved_precedence`, then `unsupported`, `dynamic_source_excluded`, `remote_source_excluded` — before the source name, and after the source name every remaining field an item is keyed by decides: its side, its limit and its status. No two items can tie, so one comparison always publishes one list. That is order, not severity: no kind is dropped, none is called worse than another, and `unsupported` carries both a file this profile merely does not accept and one whose own text would not parse, so an item behind the count may still be one to repair. The cap is unchanged at ten, and the count past it reads `N more items not listed, each ranked below those above` in the text, not only as a JSON integer.
  - **A zero-row result and a refusal name their provenance.** `Compared: base <sha> → …` and `Reproduce…` were printed only after a change, so the two answers hardest to check were the only ones that said nothing about where they came from. Both now end with those lines, in `diff`, `verify` text and the PR comment, and `review.reproduce_command` is published on a comparable result with no change. No question is asked where there is no change, and a run that names no base commit still prints neither: a provided diff or `check`, and the refusals that never reached a base — `shallow_history` and an unfetched base — which carry no block either. On a refused comparison the label is `Inputs:`, not `Compared:`, so it does not read as contradicting the `Cannot compare against …` line above it; in the PR comment a blank line separates the two from that headline where the block names no source and so prints nothing between them.
  - **No repair is prescribed for a file that parses.** An instruction file whose declared structure could not be established published `Instruction structure is unresolved (<reason>); repair or review this declared surface.` for every reason, including the many that refuse a file whose YAML is legal — a documented field in a shape this bounded profile does not accept, a key it does not list, an anchor it will not expand, a role it does not read. On one corpus repository that advice was repeated for 40 of 43 such items. Only `frontmatter_invalid`, `frontmatter_unterminated` and `instruction_text_invalid`, where the file's own text would not parse, still say `Repair or review this declared surface.`; the rest say what could not be established and that the limit may be this entry's, prescribing nothing, in wording that holds on `audit --host`, which compares nothing. For that first list to be true, `frontmatter_invalid` had to stop being the catch-all as well: a header that is legal YAML but neither a mapping nor null (`- a\n- b`, or a bare scalar) is now `frontmatter_not_mapping`, and a value this entry's own digest cannot encode — a YAML `.nan` under an undocumented key, which `json.dumps(…, allow_nan=False)` refuses — is now `structure_value_unencodable` (the digest covers the body's inline commands too, so the reason names the structure, not the frontmatter). Both take the no-repair sentence; both were and remain `unresolved` with no digest, and no file that was `structured` becomes `unresolved` — a `~` or `null` header resolves to the empty mapping `---\n---` already digests, so it keeps its digest. The issue kind, its blocking flag, the refusal it causes and the coverage `limit` are unchanged; correcting the profiles is #822.
  - **Compatibility:** the schema is extended in place — capability diff `0.3` and verifier `0.20` had not shipped before 1.1.0, which publishes both — with one constant member, `coverage.read_sources_only`. No row, digest, baseline, control state, next action or exit code moves; the only `reason` strings that move are the two split out of `frontmatter_invalid` above, which name an `unresolved` instruction structure more precisely and change no status. The README and quickstart quotes are re-captured from this tree. See the [migration note](../../STABILITY.md#host-comparison-coverage-812).

Before, `diff`, `verify` and the manifest-free PR comment printed the same "No static host-grant changes detected" for a docs-only change, for an `env` or `apiKeyHelper` edit to `.claude/settings.json` that this entry does not compare, and for a deleted settings file that held only such fields; a value-only edit left even `verifier.json`'s own inventory digests equal, because they redact those values. `compared; changed, but no grant this entry compares changed, so no row (redacted values such as env values and apiKeyHelper are not compared)` for a file that changed with no grant this entry compares changing — an `env` value, `apiKeyHelper` or MCP server `env` value edit the inventory redacts, an added `env` key, or a reordered or repeated rule; `compared; no grant this entry compares changed, but the file was not proven unchanged (redacted values such as env values and apiKeyHelper are not compared)` where both sides read the file and its bytes can be neither proven identical nor shown to differ, such as a settings file read through a link, a file under a redacted path, or a working-tree file a checkout wrote with `CRLF` (`eol=crlf`, `core.autocrlf=true`) that Git reports unchanged; the same two findings without the redacted-values note for a file the inventory reads as instructions, which holds no such value, such as a guidance edit to `AGENTS.md` or a `CLAUDE.md` link to it on a docs-only change; `compared; changed, but no row is attributed to this path` for any other changed file with no row, such as a plugin manifest whose `hooks` reference was added, retargeted or removed (its rows are on the hook files) or a retargeted link; `read in base only; 2 rows` for a deleted file and `read in head only; 1 row` for a new or untracked one such as `.claude/settings.local.json` or a hook file only the head's plugin configuration selects, but `published by head only` for a plugin manifest or marketplace, which is published only while it declares hooks; `read in head only; declares no grant this entry compares, so no row` for a new guidance-only instruction file, followed by the redacted-values note for a new or deleted settings file that holds no grant; `docs/proxy (claude-code, codex, cursor): unreadable in base and head, so neither inventory is complete` for a refused comparison; one line, `compared with no change in what this entry reads: <first three> and N more`, for the sources whose bytes are proven identical on both sides, and only those; and `N more items not listed` past the cap. What no entry shows comes first: a change with no row, a source one side read, a source not proven unchanged, then files with rows, then sources proven unchanged. In the PR comment, whose summary is bounded as a whole, the block lists only what fits in the room the entries, review question, reproduction, advisory, next action and evidence leave, at most 2000 characters, counts the rest (`N items not listed` when it lists none) and is left out when not even that fits, so it never pushes out a line the comment prints without it; a row list long enough to fill the comment still truncates it, as on `1.0.0`.
  - **JSON:** verifier schema `0.20` adds `host_comparison.coverage` and `shipgate diff --json` moves to capability diff `0.3` with the same `coverage` object: at most ten items of `{source, hosts, side, status, rows, limit, detail, scope}`, ordered so what no row shows comes first and a quiet source last, and `omitted_items`. `status` is `compared` (with `0` rows on both sides, only for a file whose blob Git proves identical, as the check `unchanged_limits` already uses does; the answer is never published), `changed_without_grant_change` (the file changed and the data shows no compared grant moved: a parsed whole file that changed in nothing but its digest, or whose content Git shows differs while its artifact did not — two blobs between commits, or working-tree bytes that differ from the base blob beyond `CRLF`/`LF`, on a path no `filter`, `ident` or `working-tree-encoding` attribute converts; never a plugin manifest or marketplace, a retargeted link or project settings while a hook's loading basis moved), `changed_without_rows`, `unchanged_not_proven` (both sides read the file, no row, no artifact change, and Git neither proved it identical nor showed it differs: a provided diff, a link read, a redacted path, a checkout line-ending conversion, a converting attribute, a mode-only change or a Git failure) or, on an incomparable result, `blocking_limit` with the issue kind in `limit`; `side` is which inventories published the source. Sources are the inventory's redacted published paths; a source named in `unchanged_limits` is not repeated; `scope` is reserved for #808 and always `null`. Runtime contract v40, unpublished before 1.1.0, is extended in place.
  - **Unchanged:** the refusal and its reasons, every row, `unchanged_limits`, inventory digests, saved baselines, `check`'s result and text, the control envelope and every control state, permission and next action (an incomparable manifest-free `verify` still routes to `audit --host`). Nothing new is discovered: a file this entry does not recognize is not listed.
  - **Compatibility:** a `0.19` verifier reads as `0.20` with `coverage: null` (not recorded) and one claiming coverage is refused; the published `docs/verifier-schema.v0.19.json` stays frozen, and a strict reader of it rejects a `0.20` `host_comparison`. The README and quickstart quotes are re-captured from this tree, the 1.1.0 build; their "not yet released" labels stand until 1.1.0 is published and move with the other published-release statements after it is. - `diff` no longer exits 1 with a traceback in a partial clone whose base objects were never fetched. In a `git clone --filter=blob:none` (or `--filter=tree:0`) clone, the checkout fetches the head's objects only, and `diff` reads the base side from Git with lazy fetching disabled, so the base archive raised a `ConfigError` (treeless, a `CalledProcessError`) with nothing on stdout and no `next_action` in agent mode.
  - **The refusal:** `diff` now exits `2` with one stderr line naming the side it could not read, the way a shallow checkout's refusal does (#683), in text and `--json`. In agent mode it emits the new error kind `objects_missing` (published in `docs/errors.json`), whose `next_actions` are `git -C <workspace> fetch --refetch --no-filter <remote>`, one per promisor remote the clone's configuration names, in configuration order. Running `next_actions[0]` and the same `diff` compares. A remote is named only when Git accepts its name as a remote name (so `up/stream` is named), it has a URL, and it does not start with `-`; no other name, `origin` included, is put in its place. When none qualifies, the one next action is a `review` and the message's example ends in a `<remote>` placeholder.
  - **What counts:** the refusal is used only when a walk of the base commit's objects fails and succeeds once objects the promisor remote still owes may be missing.
