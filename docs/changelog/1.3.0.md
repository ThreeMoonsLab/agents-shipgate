### Security

- **The capability lock records a tool's definition, so a reviewed lock sees a rewritten tool description.** A change to an MCP `tools/list` entry's description, output schema or annotations, with its name and arguments unchanged, left `capabilities.lock.json` identical in substance and `capability-lock-diff.json` reported `changed: 0, unchanged: 1`, while the PR's `capability_review` already said `tool definition changed`. That is the shape of a tool-poisoning or rug-pull change, and a later `capability diff` against a reviewed lock could not see it. Capability standard `0.6` (lock `0.9`, lock diff `0.10`) adds a `definition` block of digests to each fact built from a tool (`description_hash`, `output_schema_hash`, `annotations_hash`; never the text), a lock-level `definition_set_hash`, and `definition_changed` rows naming the parts that moved. A definition change carries no direction and does not change `release_decision.decision`. A `0.8` lock still loads, and a diff that pairs it with a `0.9` lock is refused with the re-export command. The frozen `shipgate.capability_payload/v1` and its attestation still do not carry definitions; `shipgate.capability_payload/v2` and the `capability-delta/v2` predicate do: every record's digests gain `description_hash`, `output_schema_hash` and `annotations_hash`, so a rewritten tool description is a `changed` row with direction `unknown`. `verify` writes `capability-delta-attestation.v2.json` beside the unchanged v1 file, the contract and `.well-known` name the v2 identities, and `tools/verify-capability-delta.py` 1.1.0 verifies both versions (#1117).
- **A secret or prompt-injection phrase in a tool description is published as a finding, with the value redacted.** `SHIP-DOC-SECRET-IN-DESCRIPTION` and `SHIP-DOC-INJECTION-RISK` matched a live `sk_live_` key or "ignore all previous instructions" and then dropped the finding, because a regex match has no policy-eligible support: `report.json` had no finding, SARIF no result, and `report.md` said only that policy applicability was inferred, while the same secret in an n8n workflow (`SHIP-N8N-SECRET-IN-WORKFLOW-PARAMETER`) was published. All three now follow one rule and are always visible in `report.json`, `report.md`, SARIF and the packet. The two description findings stay `support.policy_eligible: false` and `agent_action: informational`: they are never a blocker or a named review item and change no exit code, and the `insufficient_evidence` gap beside them is unchanged except that its `why` now leads with the check's catalog description ("Tool description contains a secret-like value."), as every finding-derived gap now does. Whether a lexical match may move a verdict is #1055. Migration: [STABILITY.md](STABILITY.md#secret-observations-1026). (#1026)
- **Redaction covers four more secret shapes, two more credential labels and a finding's extra fields.** `Authorization: Basic <credential>`, a PEM private-key block, a Google `AIza` key and an AWS secret access key written without a label appeared verbatim in `report.json`, `report.md`, SARIF and the packet wherever free text carried them, such as `agent.declared_purpose` or a tool name. The shared rules now redact all four (`basic_auth`, `private_key`, `google_api_key`, `aws_secret_access_key`), an `authorization`, `proxy-authorization` or `auth` labeled value after an optional scheme word (the scheme alternation the host-grant readers use; a `Digest` value to the end of its line), and `Bearer` followed by a tab. A `Basic` token counts only when it decodes to `user:password`, so prose such as `Provides Basic ReadOnly access` is neither redacted nor reported, and a 40-character run that reads as camelCase words or path segments (`getCustomerOrderHistoryForAccountV2Async`, `Sources/PaymentKit/Handlers/RefundTools2`) is not taken for an AWS key, so a SARIF alert keeps its file. The first three also raise the secret findings above and skill `SEC-SECRET-001`; the AWS shape and the labels only redact, because without a prefix or a credential label they are too common to report. `sanitize_model` now walks the extra fields of an `extra="allow"` model, so a value a check plugin attaches to a `Finding` is redacted before any writer sees it and counted in the privacy audit. `privacy_audit.rules_version` is `0.2`. A finding whose evidence held one of these shapes publishes a new fingerprint; re-save a baseline that recorded it. (#1026)
- **Redaction also covers an AWS secret access key inside a path or URL segment, and a `Basic` credential in URL-safe or unpadded base64.** `path/<key>`, `s3://bucket/<key>/obj` and `https://host/<key>?a=1` kept the key verbatim, as did such a `Basic` token with no credential label before it; a path that reads as words is still not taken for a key. (#1082)
- **Two credential shapes are no longer published.** The token after an `Authorization:`, `Proxy-Authorization:` or similar header's scheme (`Bearer`, `Basic`, `Digest`, `Token`, `Negotiate`) was published in rule, hook and MCP argument text, because the header pattern took the scheme word as the value; the password in `curl -u user:password`, `--user`, `--user=` and `--proxy-user` was never read as one; and `--password=value` and similar `--flag=value` credential spellings are now withheld like their space-separated forms. A rotation of these values is now quiet, as for every other withheld value, so a saved baseline or the first comparison across this change shows such a hook or rule once as changed. Only the credential is withheld: the header name, the user name and an unrelated `-u` flag (`sort -u`, `git push -u`) are published as before. (#987)
- **`bootstrap` no longer runs code committed in the repository it adopts.** Each step re-entered the CLI as `python -m agents_shipgate` with the workspace as the working directory, and `python -m` puts that directory first on `sys.path`: a committed `yaml/`, `typer/`, `pydantic/` or `agents_shipgate/` package was imported and executed before `detect` read anything. The steps now run as `<sys.executable> -P -m agents_shipgate`, and so does every recovery command a `python -m agents_shipgate` run prints (`next_actions[].executable` is four tokens). `-P` drops only the working directory; `PYTHONPATH` and the environment still reach the child, with relative and empty `PYTHONPATH` entries anchored where `bootstrap` was started rather than resolved inside the workspace. Regression tests plant both packages, and a `yaml/` under a relative `PYTHONPATH` entry, and require bootstrap to finish without importing any of them. (#1020)
- **`capability export` and the MCP `shipgate.capabilities` tool load plugins only on the opt-in.** Both passed an explicit `plugins_enabled=True` unless `--no-plugins` was given, so a read-only tool imported every installed `agents_shipgate.adapters` entry point with `AGENTS_SHIPGATE_ENABLE_PLUGINS` unset, where `scan` and `verify` imported none. They now honour the same opt-in, `--no-plugins` still wins, and the lock's `source.plugins_enabled` records the value that took effect (`false` by default, which moves `source_set_hash`). An adopter whose lock includes tools read by a third-party adapter sets the variable for `capability export`, as `scan` already required. (#1020)
- `docs/trust-model.md` lists every process Shipgate starts — the Git plumbing behind `verify`, `check`, `diff` and the Claude Code hooks, workspace discovery, `bootstrap`'s self-invocation, fixture Git, the `authorization execute` HTTPS push and the native prover — instead of saying it shells out only for Git discovery. `tests/test_adapter_static_only.py` fails when a spawn site is added, removed or moved without that table changing, when a `-m agents_shipgate` argv lacks `-P`, and now also on `asyncio.create_subprocess_*`. Migration: [STABILITY.md](STABILITY.md#exec-trust-opt-in-1020). (#1020)

### Verification, attestation and control

- **`verify` stops when it has no base, and a deleted manifest is a removed gate.** With neither `--base` nor `--no-base`, a run whose detection found nothing (a default branch other than `main` or `master` with no `origin/HEAD`, or a repository with no remote) read no committed change, published that empty change set as `complete` and granted merge: a pull request deleting `.github/workflows/agents-shipgate.yml` on a `develop` repository exited 0 as `mergeable`, and exited 20 as `blocked` once `--base origin/develop` was named. Detection keeps every base it found before and otherwise follows `check`'s ladder (#649): a default branch already at the head is an empty comparison, and a repository with no remote uses its local `main` or `master`. When nothing resolves, the run exits 2 with `base_status: ref_missing`, a `diff_status` of `unavailable`/`refs_missing` whose detail begins `base_unresolved`, a `fetch_base` next action naming `--base` and `--no-base`, and every permission denied. A change deleting the configured manifest that its merge base (or `HEAD`, for a working-tree run without a base) holds is a human `stop` naming the removal, exit 2, instead of the `configure` and `init --write` route; a missing manifest whose base cannot be resolved fails closed as above, one whose base holds it but cannot be compared (a shallow merge base), or whose named `--base` is not available locally (the Action's `diff_base: target` without `fetch-depth: 0`), fails closed with that diff-input `fetch_base` stop in both CI modes, and a repository that never had one keeps the setup route (with an unavailable named base, only where complete history, neither shallow nor grafted, shows the manifest never existed; a depth-1 checkout with an unfetched `--base` therefore stops in advisory mode too, where it used to exit 0 on the host route). `SHIP-VERIFY-CI-GATE-REMOVED` resolves changed paths against the evaluated tree's root instead of the manifest's directory, so `apps/agent/shipgate.yaml` no longer turns a comment in the root workflow into a critical blocker, nor lets a nested copy hide a root deletion. Every Git archive packs the commit's tree rather than its history, so a depth-1 checkout archives `--head` instead of failing an integrity check that agent mode routed to editing `shipgate.yaml`. `check` leaves verify's default reports directory out of a working-tree change set when it holds only uncommitted Shipgate artifacts, so a check, verify, check loop no longer counts the reports as changed files. **A run that used to report `mergeable` with no base now exits 2**: pass `--base` (in the Action, `diff_base: target` with `fetch-depth: 0`, or `base_ref`) or `--no-base`. No schema, contract or check ID moves. See the `verify stops without a base` migration note in `STABILITY.md`. (#1023)
- **`verify` reads an in-repository `--diff-from` and the exit policy from the base, not from the change under review.** A `--diff-from` path inside the repository was opened in the checkout, took the place of the `--base` scan, and was not a trust root: a pull request that added a destructive tool and regenerated `ci/base-report.json` from its own head compared the head with itself and could come back `mergeable` with `trust_root_touched: false`, and `SHIP-VERIFY-POLICY-WEAKENED` read its base policy from that same file. When a base resolves, such a path is now read as the base commit holds it (a file the base does not hold as a regular file is replaced by a scan of the base, and `base_notes` says which); a path outside the repository is the operator's and is read where it is, as is any path when there is no base (`--no-base`). An in-repository `--diff-from`, `--baseline` or `--policy-pack` file the change edits is a touched trust root (`SHIP-VERIFY-TRUST-ROOT-TOUCHED`, class `shipgate_state` for the first two and `policy` for a pack), unless the trust-root table already classifies it. Without `--ci-mode` and `--fail-on`, `ci.mode` and `ci.fail_on` came from the head's manifest, so changing `mode: strict` to `mode: advisory`, or dropping a severity from `ci.fail_on`, in the pull request turned exit 20 into exit 0 while the verdict stayed `blocked`. With a base and without `--ci-mode`, `ci.mode` now resolves to the stricter of the base and head manifests (`strict` if either declares it, named in `base_notes`); `--ci-mode` remains the operator's override, and a change that adopts `strict` still takes effect in the same pull request. Without `--fail-on`, the base's declared `ci.fail_on` is a floor for the exit code only, with or without `--ci-mode`: an active finding of a severity the base declares exits 20 (`fail_policy.exit_code`, `would_fail_ci`), and `base_notes` names the severities. The blocker severities, the verdict and `fail_policy.fail_on` keep the change's list, so a loosened list stays the human-review route `SHIP-VERIFY-POLICY-WEAKENED` reports (the governance benchmark is unchanged) and fails CI until a human handles it. **A workflow that pointed `--diff-from` at a report regenerated inside the pull request, or that relied on the head manifest to relax `ci.mode` or `ci.fail_on` (including through the Action, which passes `--fail-on` only when its `fail_on` input is set), now sees the base's comparison and the base's exit floor.** No schema, contract or check ID moves. See the `verify reads PR-controlled inputs from the base` migration note in `STABILITY.md`. (#1024)
- **A policy pack the manifest declares is a trust root wherever it lives.** `SHIP-VERIFY-TRUST-ROOT-TOUCHED` classified a pack only by `**/policies/**`, while `checks.policy_packs[].path` may name a file anywhere under the manifest's directory, so a pull request that edited nothing but a pack declared elsewhere, such as the `vendor/shipgate-policies/org-release.yaml` that `docs/organization.md` recommends, raised no finding and could come back `mergeable`. #1024 covered a pack named with `--policy-pack`, not one the manifest declares. `verify` now treats every pack the base or head manifest declares as a `policy` trust root, resolved against the manifest's directory as the scan resolves it, with `matched_glob` set to that path. The base's declarations are read from the base commit, so a change that removes a declaration and edits the pack in the same diff still touches it. The audit log that vouches for an in-repository `--baseline` (`baseline.audit_log`, or `baseline-audit.log` beside the baseline) is a `shipgate_state` trust root too, unless `baseline.integrity_mode` is `off`. A path the trust-root table already classifies, such as `policies/org.yaml`, keeps its class, glob and fingerprint; a newly covered path gets a new fingerprint. No schema, contract or check ID moves. See the `the policy a manifest declares is a trust root` migration note in `STABILITY.md`. (#1075)
- **`checks.ignore` no longer turns a configured advisory gate green while the decision says `blocked`.** A suppression cannot waive a mandatory current-surface control (the four dedicated control families, such as `SHIP-ACTION-FINANCIAL-WRITE-CONTROL-MISSING`, and engine-raised control-pack obligations), so the release decision kept such a finding as a blocker; the exit code dropped it with every other suppressed finding before matching `fail_on`. `samples/support_refund_agent` in advisory mode with `fail_on: [critical]` and three `checks.ignore` entries printed `Decision: blocked`, `would_fail_ci=false` and exited `0`; without the entries it exited `20`. The exit code now also reads the decision's `blockers[]`: a blocker whose severity is in `fail_on` (including `verify`'s base `ci.fail_on` floor) exits `20` in either mode, for `scan`, `verify` and the Action, and `fail_policy.exit_code` / `would_fail_ci` in `report.json` and `verifier.json` say the same. Strict-mode exit codes are unchanged, because a blocker already meant a `blocked` decision, which strict mode fails; advisory mode without `fail_on` still exits `0`; and a suppression still waives every other finding. A report whose blocker in `fail_on` would not fail CI is refused when it is written. Separately, `verify-run.json`'s outcome, the verification receipt and the safety qualification script now read the decision-to-merge-verdict projection from `schemas/verifier.py` instead of carrying their own copies of its table, which would have refused every verify run the day that table changed; a test refuses a new copy. Migration: [STABILITY.md](STABILITY.md#release-decision-truth-table). (#1029)
- **Each baseline verifies against its own audit rows, the override tier gate reads the severity a finding was emitted at, and an optional policy pack's pin is fatal.** Every baseline in a directory appends to one `baseline-audit.log`, and verification compared a baseline with the log's last row whoever wrote it: saving `baseline-prod.json` turned an untouched `baseline.json` into a critical `SHIP-BASELINE-INTEGRITY-MISMATCH` (`baseline verify --strict` exit 6, `scan` `blocked`), while a copy of the baseline saved last verified clean. Verification now uses the latest row recorded for that baseline's file name; a log with no row for it is `missing_audit_log`, naming the files the log does record and the `baseline save` that records it. Audit logs written by released versions verify unchanged. The baseline hash reads CRLF as LF, as it always has (a Windows checkout converts line endings on an untouched file); its docstring, which said line endings were detected, now says so. `checks.severity_overrides: {SHIP-SIDEFX-IDEMPOTENCY-MISSING: high}` lowered that check's `critical` finding (emitted when a retry policy is known) with no acknowledgement, because the tier gate compared with the `high` catalog default; it now compares with the strongest severity among the findings the override would lower, so the override needs an `acknowledge_overrides` entry (exit 2 otherwise), and the same holds through a legacy alias such as `SHIP-API-OPERATIONAL-READINESS`. An `optional: true` policy pack whose `sha256` pin did not match, or that had been replaced by a malformed file, a directory or a link, was a warning and its rules were dropped; `optional` now tolerates only a missing pack, and anything else is a config error. Migration: [STABILITY.md](STABILITY.md#trust-config-1030). (#1030)
- **`attest`, `org bundle` and the Action validate the verification receipt of current verify output.** All three gated receipt validation on version literals the engine had stopped emitting (verifier `0.5`–`0.7`, `shipgate.verify_run/v3`). On every completed `1.x` verify run, `attest --from agents-shipgate-reports/verifier.json` and the Action's `attestation: true` step crashed with a traceback and exit 1, `org bundle` published a rewritten `receipt_id` or `decision_id` with exit 0, and the Action exported empty `request_id`, `receipt_id`, `decision_id` and `artifact_set_id` beside a `verification_receipt_json` nothing had checked. One predicate, `requires_verification_receipt` in `agents_shipgate.schemas.verification_identity`, now decides for all three: it names the verifier versions written before receipts (`0.1`–`0.4`) and reads every other version, newer ones included, as owing a receipt whenever the verifier states an outcome; the Action, which also publishes `report.json`'s decision, owes one whenever `verifier.json` names a `report.json` as its own, and publishes nothing from a report it does not name (the manifest-free host route leaves an earlier run's in place). A `0.1`–`0.4` label on a payload carrying a receipt-era identity field (`request_id`, `decision_id` and the four others verifier `0.5` added) is not believed. A failed or not-run execution that states none (a missing manifest, the manifest-free host route) writes no receipt, and still publishes, with empty identities. A receipt that is present is always validated: its content addressing, every artifact it binds and the request and decision `verifier.json` names. A missing, tampered or mismatched one exits `3` in `attest` and `org bundle` with one line naming the receipt (plus the agent-mode `next_action` line), and fails the Action's output step. `org bundle` also refuses an `attestation.json` whose receipt identity is not the validated receipt's, or that names one when none was validated. The Action's `verification_receipt_json` is empty unless the receipt validated. No schema version changes. See the [migration note](STABILITY.md#receipt-predicate-1022). (#1022)
- **An attestation can record who approved the change.** `org.actor` is who triggered the run and `human_ack` is what the manifest declares; neither is an approval by a second person. `agents-shipgate attest --reviews <file>` reads the JSON array the pull request reviews API returns, fetched by the workflow into a file outside the repository, and records an `approval` block (attestation `0.6`): `approved`, `approved_stale`, `changes_requested` or `not_approved` against the attested head commit, the approvers, any standing change requests, and approvals by the author or a bot, which never count. A reviews file inside the repository or `GITHUB_WORKSPACE`, or one naming another pull request, is refused with exit `3`. Without `--reviews` the block reads `status: not_supplied`. The approval never changes the verdict or an exit code. `registry ingest` copies it (registry `0.5`), `registry summary` counts `by_approval_status`, and rows written by earlier releases keep their ids and chain. The attestation's capability-lock binding also records the lock's `definition_set_hash`, and its diff summary `definition_changed` (#1118).
- Control completion now requires an explicitly evaluated subject. Unreadable MCP configuration or policy, empty/irrelevant MCP input, and detached `check` diffs deny every permission even when their diagnostic decision is `allow` or `warn`. `mcp audit` also applies `check`'s structural diff validation to MCP source records and to records whose path cannot be parsed, so a binary or header-only record (a binary rename included), a rename without hunks that git does not report as 100% similar, an empty file's record printed without hunks, two records for one path, or an unreadable path is unread input, not an evaluated source, and the stop's `summary` gives that reason. A replayable clean checkout remains an evaluated boundary result. Verifier skip completion requires an evaluated negative trigger over complete input; provisional skipped results are no longer constructed before input failures are resolved. Stored explicit permission vectors missing any of the six fields are rejected by the shared control, compact envelope and `current-control.json` pointer runtime readers, matching their existing published schemas. No frozen schema grammar changes. See the `evaluated subject` migration note in `STABILITY.md`. (#930)
- **An empty preflight plan no longer grants merge or completion.** A plan that named no changed file, capability request or host permission request returned the shared `complete` state, whose permissions include `merge` and `report_complete`, with no verifier run behind it. Preflight `0.6` answers it with the new `planning_only` state, which owes no action and authorizes nothing, and every preflight route now denies every permission in both the model and the published schema; `complete` and `review_publishable` cannot appear. Docs-only plans still route to `verify`, and protected surfaces and drift still stop for a human. `0.5` stays frozen and readable as a base preflight. Runtime contract 41 → 42; `minimum_control_contract_version` stays 21. Hooks written by `install-hooks` before this change accept only preflight `0.5`, so their instruction-structure check fails closed until `install-hooks --write` is re-run. See the `planning-only preflight` migration note in `STABILITY.md`. (#610)

### Host comparison

- **Host diff reads Claude Code permission rules the way Claude Code documents them.** One rule model, shared by `diff` (text and `--json`), `verify`'s host comparison, `check` and `audit --host --drift`, replaces set-membership comparison of `allow`, `ask` and `deny` rules, scoped to one host, settings source and disposition. A documented respelling (`Bash(git add:*)` ↔ `Bash(git add *)`, `Bash(*)` ↔ `Bash`) is one `respelled` change and no widening, for a deny rule too (#918). An added allow rule that an allow rule the same source declared at the base already matches — an unchanged `Bash(git *)` over `Bash(git merge --no-ff -X ours:*)` (#941), a removed `Bash(gh pr *)` over the four subcommands that replace it (#918), a bare `Edit` over `Edit(**/.env.example)` (#969) — stays a row and is not a widening; the removed broad rule names the rules it was narrowed to. `Edit(**/.env.example)` is a scoped rule, not "every target of this kind", and no longer blocks as a wildcard (#969). A `Read(!…)`/`Edit(!…)` deny or ask rule is described as a carve-out of the earlier rules it follows in the same source, or as excepting nothing when listed first; it widens only when it now follows a rule the source already declared, and an ordering-only edit that changes that is a row (`carves_from` on the grant, host-grants `0.9` extended in place; `check` raises `SHIP-HOST-BOUNDARY-PERMISSION-DENY-REMOVED` with evidence kind `permission_deny_carved_out`) (#974). A path-scoped `Write`, `NotebookEdit`, `Glob` or `MultiEdit` rule, which Claude Code accepts and never consults, is reported as such and is never an effective grant, a removed denial or a widening; a bare `Write` rule is unchanged (#938). Anything the model cannot prove stays a widening: shell syntax, an exec wrapper, a `**` or a `*` crossing `/`, a differently cased tool name, an unanchored allow `*` (which Claude Code skips), a deny→allow move and an addition beside a lifted restriction of the same tool. The #918 reproduction now shows 3 widenings, not 9. See the `Claude Code permission-rule model` migration note in `STABILITY.md`. (#918, #941, #969, #974, #938)
- **A Claude Code setting that runs a command, or an `env` entry that redirects requests or loads code, is a host-grant row, and a settings change no row shows is no longer "no change".** Adding `"statusLine": {"command": "curl … | sh"}`, `"apiKeyHelper": "curl … | sh"`, `env.ANTHROPIC_BASE_URL` or `env.NODE_OPTIONS` to `.claude/settings.json` gave no row: `diff` (text and `--json`), `verify`'s host comparison and the PR comment headlined `No static host-grant changes detected. No verdict is implied.`, and `audit --host` reported Claude Code coverage `complete`.
